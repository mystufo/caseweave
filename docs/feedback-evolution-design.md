# 负反馈进化闭环 — 设计文档

> 状态：**第一步（后端闭环）+ 第二步（前端总览面板）均已实现 2026-07-06**。
> 实现要点见 record.txt 同日两条变更记录。
> 背景：Phase 4.2 二阶段（prompt 改进建议）验收中，用户提出两个问题：
> ① 每次点「生成建议」都重新分析同一批负反馈，历史反馈被反复调用，不合理；
> ② 负反馈不该只喂 prompt，还应能优化/修改 Skill，现在只放 system prompt 不够全面。
> 本文档厘清现状、指出两个问题的共同根因，并给出分级方案供决策。

---

## 一、现状：负反馈已有三个消费出口（但各自为政）

| 出口 | 实现 | 触发方式 | 消费的信号 | 产物 |
|------|------|----------|-----------|------|
| **① 知识沉淀** | `agents/diff_analyzer.py`（4.1） | edit 反馈**自动**触发后台 `_analyze_diff_bg` | "修正业务规则"类 edit | `KnowledgeEntry`(source=user_feedback) |
| **② Skill 归纳** | `agents/skill_generator.py`（4.1） | 「测试设计经验」抽屉**手动**点「自动归纳」 | 按模块聚合 edit 的 diff_analysis + 反馈衍生知识 | 模块级 `Skill`(auto_generated) |
| **③ Prompt 建议** | `agents/prompt_optimizer.py`（4.2 二阶段） | 「系统提示词」**手动**点「分析负反馈生成建议」 | 指向通用设计缺陷的 edit | `PromptSuggestion`(pending) |

**关键事实（已核实代码）：**
- `routes_feedback.submit_feedback`：**只有 `feedback_type=='edit'` 且有真实字段变化时**才 `asyncio.create_task(_analyze_diff_bg)`。`dislike`/`like` 落库后**不触发任何后台处理**。
- 三条线的样本聚合都过滤 `diff_analysis IS NOT NULL`——而 `diff_analysis` 只有 edit 才会被写入。

---

## 二、由此暴露的四个问题

### 问题 A — dislike 反馈零贡献（隐藏缺口）
`dislike` 从不产生 `diff_analysis`，因此**三条出口全都取不到它**。用户点👎表达了不满，但这个信号目前完全没有进入任何进化链路。prompt_optimizer 的样本查询虽写了 `in_(("dislike","edit"))`，但被 `diff_analysis IS NOT NULL` 过滤掉，实际只有 edit 生效。

### 问题 B — 同一批反馈被反复分析（用户问题①）
没有"这批反馈已被消化"的水位线标记。后果：
- 采用建议成 v4 后，促成 v4 的那批反馈仍在池子里，下次生成又被 LLM 分析一遍 → 大概率重复提一个已解决的改动。
- 已有 pending 时 `run_generator_suggestion` 会挡住重复生成（不浪费 LLM），但采用/忽略后这道防护即失效。

### 问题 C — 缺分诊，反馈可能去错出口（用户问题②的深层）
不同 intent 的负反馈本应去不同出口：
- **修正业务规则**（如"积分不足跳订阅页"）→ 属**产品知识**，归宿是知识库/Skill；改通用 prompt 属归因错误。
- **补充边界用例 / 调整步骤模糊** → 属**通用测试设计缺陷**，归宿是 generator prompt。
- **某模块反复同类修改** → 归宿是该模块的 Skill。

这正是验收时 `__NO_SIGNAL__` 的由来：3 条"修正业务规则"被 prompt_optimizer 正确拒绝（它们该进知识/Skill），但系统**没告诉用户"它们应由另一条线消费"**，用户误以为功能没生效。

### 问题 D — 入口分散，用户无法感知"反馈在被多处消费"（用户问题②的表层）
三条线散落在两个抽屉（测试设计经验 / 系统提示词）+ 一个全自动后台，用户感知不到它们是一个进化体系，自然会觉得"只放了 prompt、不够全面"。

---

## 三、共同根因

**缺一个统一的「负反馈分诊 + 消费台账」中枢。** 一条负反馈进来应当：
1. 归一化（edit 与 dislike 都能进）；
2. 按 intent **分诊**到 知识 / Skill / Prompt 三个出口之一；
3. 被某出口消费后**标记已消费**（台账 / 水位线）；
4. 各出口只处理未消费的**增量**。

补上这个中枢，问题 B（重复）与问题 C/D（不全面/去错）一并解决；问题 A（dislike）在归一化那步捎带修掉。

---

## 四、分级方案

### 方案 1 — 只修 prompt 去重（最小）
- prompt_optimizer 生成时把"本次分析到的最大 feedback id"记进 `PromptSuggestion.evidence`；
- 下次生成只取 id > "上一条**已采用**建议的水位线" 的新反馈；
- **dismiss 不推进水位线**（否的是建议，不是反馈）。
- 无需改表。**只解决问题 B**，Skill/知识/dislike 现状不动。
- 工作量：小（1 个 agent + 1 个路由函数）。

### 方案 2 — 加「反馈进化」总览面板（感知层）
- 方案 1 的去重 + 知识库页新增一个「反馈进化」总览：把三条线的入口、最近产物、待处理项集中展示；
- 各出口内部逻辑不变，只做聚合呈现 + 让用户看到"反馈流向了哪里"。
- **解决 B + D**，缓解"不够全面"的感知问题。
- 工作量：中（主要在前端聚合 + 一个只读汇总 API）。

### 方案 3 — 统一分诊 + 消费台账（治本，大改）
- 新增分诊层：edit 归一 + dislike 归一（问题 A）→ 按 intent 打 `target ∈ {knowledge, skill, prompt}` 标签；
- 新增消费台账（可复用 Feedback 表加列，或新表）：记录每条反馈被哪个出口、哪个产物消费；
- 三条出口改为"只吃 target 匹配且未消费的增量"，产物落地时回写台账；
- 前端总览面板展示分诊结果与消费状态。
- **一次性解决 A/B/C/D**。
- 工作量：大（跨 4.1 + 4.2，涉及 Feedback 模型、三条 agent 的取数口径、一次迁移、前端面板），已超出"Phase 4.2 二阶段"范围，更像"反馈进化收口"专项。

---

## 五、推荐

- 若只想让二阶段验收干净收尾：**方案 1**（当下就能做，风险低）。
- 若认可"反馈进化应是统一体系"这个方向、愿意立专项：**方案 3**，但建议拆成两步走——
  1. 先做方案 1 的去重 + 问题 A（让 dislike 也能进链路）；
  2. 再做分诊 + 台账 + 总览面板。
- 方案 2 可作为方案 3 第二步的前置产物（先让用户"看得见"，再逐步"分得准"）。
